## 1) Цель и описание задачи

**Цель**: создать интерактивного Telegram-бота для преодоления языкового барьера путём имитации живого общения на английском языке с мгновенной обратной связью по ошибкам.

**Основные задачи**:

- **Снятие страха ошибки**: бот выступает в роли дружелюбного собеседника (Persona-based AI).
- **Контекстное обучение**: исправление ошибок происходит непосредственно в процессе диалога, а не в отрыве от него.
- **Доступность**: использование SQLite для легковесного хранения данных и AI-агент с Timeweb.

## 3) Требования к API и моделям данных

### 3.1) Модели данных (SQLite)

Используем **асинхронный движок** (например, SQLAlchemy + aiosqlite).

#### Политика хранения данных (MessageHistory)

- **Срок хранения**: хранить историю сообщений не дольше **90 дней** (допустимая альтернатива: **30 дней** для более строгой приватности).
- **Очистка**:
  - Пользователь может очистить историю через команду **`/privacy`** (минимум: “очистить историю диалога”).
  - Также поддерживать серверную очистку по TTL (периодический job/скрипт), удаляющую записи старше срока хранения.
- **Примечание**: `MessageHistory.content` потенциально содержит персональные данные — хранить минимально необходимое и не передавать в LLM больше, чем нужно для текущего контекста.

#### `User`

| Поле | Тип | Описание |
|---|---|---|
| `id` | BigInt | Telegram ID, Primary Key |
| `username` | String | Username |

### 3.2) AI-агент (LLM)

- **Интеграция**: REST API (OpenAI-compatible через Timeweb Cloud). Документация: `https://agent.timeweb.cloud/docs?roistat_visit=9409636`
- **Формат ответа**: для стабильной работы рекомендуется запрашивать **JSON** от модели (JSON Mode), чтобы разделить «ответ собеседника» и «блок исправлений».
- **Контекст**: ограничение истории диалога (Memory Buffer) — не более **10** последних сообщений для экономии токенов и поддержания актуальности.

#### Контракт JSON-ответа (пример)

Ожидаемый JSON (пример структуры):

```json
{
  "reply_text": "Sure! Tell me more about your day.",
  "corrections": [
    {
      "raw": "I goed to school",
      "corrected": "I went to school",
      "explanation": "Past tense of 'go' is 'went'.",
      "type": "grammar"
    }
  ],
  "follow_up_question": "What was the most interesting part?"
}
```

- `reply_text`: основной ответ “собеседника”.
- `corrections[]`: список исправлений (может быть пустым).
- `follow_up_question`: вопрос для продолжения диалога (опционально).

### 3.3) Нефункциональные требования (надёжность и защита)

- **Rate limit / антиспам**: ограничить частоту сообщений на пользователя (например, \(N\) сообщений в минуту) и/или ввести cooldown при флуде.
- **Обработка флудящих пользователей**: временная блокировка/замедление, понятное уведомление пользователю, логирование инцидента.
- **Таймауты запросов к LLM**: на запрос к LLM должен быть установлен таймаут; при превышении — graceful fallback (сообщение пользователю + повторить/сократить контекст).
- **Ретраи с backoff**: для сетевых ошибок/429/5xx — несколько попыток с экспоненциальной задержкой и джиттером; обязательный предел попыток.

### 3.4) Требования для монетизации (подписки и лимиты)

- **Планы и лимиты**: описать тарифы (минимум `free` и `pro`) и их лимиты (сообщения/токены/скорость), а также доступ к функциям (например, “расширенные исправления”, “больше контекста”).
- **Единая проверка доступа**: проверки “можно ли пользователю использовать фичу/чат” должны выполняться в **слое `services`** (например, метод `check_access(user, feature)` / `can_chat(user)`), а не размазываться по хендлерам.
- **Тарификация/контроль себестоимости**:
  - хранить `tokens_in/tokens_out` в `MessageHistory` и агрегировать их в `Usage`;
  - логировать ограничения/отказы (лимит превышен) для последующей аналитики.
- **Миграция при росте**: при увеличении нагрузки SQLite может стать узким местом (конкуренция на запись). Архитектуру и модели проектировать так, чтобы миграция на Postgres была прямолинейной (через SQLAlchemy/Alembic).

## 4) Переиспользование компонентов

В проекте следует опираться на стандартные модули экосистемы Python:

- **aiogram 3.x middlewares**: автоматическая регистрация пользователя в БД при каждом сообщении.
- **FSM (Finite State Machine)**: управление состояниями (например, ожидание ответа в чате или выбор уровня языка).
- **Pydantic**: строгая валидация конфигов (токены, эндпоинты API).

- [ ] Реализована асинхронная работа с БД (никаких блокирующих вызовов в хендлерах).
